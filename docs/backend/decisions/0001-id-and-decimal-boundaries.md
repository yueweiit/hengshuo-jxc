# ADR 0001：安全整数 ID 与十进制接口边界

日期：2026-10-15。状态：M0 技术决策；具体 DTO 的实施与真实 PostgreSQL 验证分别留证。

现有 Vue/Mock 以 `Number(id)` 读取 ID，JSON 金额也是 number。直接输出任意 Java Long 或把金额改成字符串都会破坏当前契约。

一期使用 PostgreSQL 共享 sequence 产生正 bigint ID；数据库、DTO 和路径转换同时约束 `1 <= id <= 9007199254740991`。不使用会超出 JavaScript 安全整数范围的雪花值。ID 在 JSON 中继续为整数 number。以后需要完整 64 位 ID 时，单独迁移为字符串并同时改调用方，不能静默切换。

金额、数量、汇率由 JSON 原始十进制 token 直接解析为 BigDecimal，计算、校验和持久化不经过 double。数据库保留金额 `numeric(20,4)`、基础数量 `numeric(18,4)`、汇率 `numeric(18,8)`，中间单位成本/除法采用更高精度；最终行金额按币种 HALF_UP 再汇总。

JSON number 的技术边界必须小于数据库可存范围。一期建议透明限制：金额/数量绝对值不超过 `100000000000`，小数位最多 4；汇率绝对值不超过 `1000000`，小数位最多 8，具体是否严格为正仍由业务字段定义。这些量级为浏览器保留离散小数显示余量；它们是序列化技术边界，不是采购、授信或审批额度。仅限制“放大后整数 <= MAX_SAFE_INTEGER”不足以证明高量级小数不会在二进制 number 中塌缩。

拒绝非有限、超范围或超精度输入，返回受控业务错误；不能静默截断或舍入来通过 DTO 校验。服务端金额始终以 BigDecimal 为依据，浏览器预览不能成为事实来源。只读响应也需遵循相同边界，不能把超限事实偷偷转成字符串、零或近似值。DTO 实施若采用更严边界，应在此处和配置清单一起更新，并保留兼容说明。

已核对当前 `freshDb()` 加现有双国家 scenario 的演示样本：金额类最高观察值 `299968.62`（`approvalInstances[].facts.amount`），数量类 `3400`（采购单 totalQty），汇率 `2.5301`。扫描的是 key 含 amount/price/cost/creditLimit/balance、qty/quantity、rate 的有限数值；不是对所有派生数值的完备证明，更不是生产数据。现样本远低于建议边界，不能据此臆造生产业务上限或确认未来历史导入兼容。

验收要求：安全 ID 上下边界、超界/非整数；4/8 位小数与超精度；原始 JSON 小数无 double 中转；负数是否允许按字段/动作区分；同一请求的 DTO 拒绝不能留下幂等占位或半笔事实。完整生产历史数值分布仍待迁移演练核对。
